# V24 判据做实 · 真实现场裁定（`v24-integrator` / task-6）

**裁定：`复现`（macOS 本机，v0.7.0 = HEAD `14ba709`，真实现场）。**
并且在**同一台机器、同一判据**下拿到了回落证据、重复证据、功能正对照、以及触发与连接数的关系。

---

## 0. 一句话

在 wasm 服务端（干净 HEAD 构建，sha256 `99efd472…`）+ 官方 Xray 26.3.27 客户端 + **300 条 CONNECT 指向不可达目标悬停**这个真实现场里：

* **idle**（官方客户端起着、不发请求）：`marginal = -0.0001` 核
* **hover 300 条**：`marginal = 1.0862` 核（跑满一核），40s 窗口实测 `cpu = 38.63s / 40s = 96.6%`；**重复一遍 35.46s（88.6%）**
* **同场景功能正对照**：hover 期间经隧道 `curl` = **000**（实例已被占死）；idle 同命令 = **200**
* **回落实验**：悬停 12s 后把连接全部关掉 → `marginal = -0.9886`（回落）
* **60 条不触发**（`marginal = 0.0008`）；`100/150/200/250` 条也不触发；`256` 条**触发**（31.08s/35s）；`270` 条不触发；`300` 条触发

⇒ V24 在这台 macOS 上**不是「不复现」，而是复现**，且触发对连接数/时序敏感。

## 1. 为什么之前会以为「不复现」（方法论更正，比结论本身重要）

1. **lead 早先跑的「最小探针不复现（idle 1.1% / hover 2.3%）」测的不是产品路径。**
   `CARGO_TARGET_DIR=$PWD/target cargo build --examples -p xt-wasm-runtime` 在本机产出的是
   **Mach-O 宿主二进制**（`file` 实测），走 `xt-wasm-runtime/src/host.rs` 那条
   「`WouldBlock` 后让出 1ms 重试」的**调试实现**，根本没有 WASI pollable。
   拿它证明「V24 不复现」等于测错了对象。
2. **换成真 wasm 之后，又不能只看绝对值。** 本机 `wait4` 的 rusage 绝对值偏低
   （lead 已校准：2.0s 纯忙循环只报 1.09s），且 wasm 服务端每次启动都要 JIT 编译
   （`-C cache=n`）——那段常数开销会按窗口长度稀释。所以判据必须是**两个窗口的差分**：

   ```
   marginal = (cpu@W2 − cpu@W1) / (W2 − W1)      1.0 = 跑满一核
   ```

   常数开销相减即消。idle 的 marginal ≈ 0，自旋的 marginal ≈ 1，这是**可证伪**的。
3. **单侧判据会骗人（V24 十九续的教训）**：每个场景里都塞了一次真实转发（`curl` 经隧道）。
   本次正是靠它区分出「真自旋把实例占死（curl=000）」与「空闲但活着（curl=200）」。

## 3. 两组数字 + 全部证据

### 3.1 主表（`target/v24-field-head/report.txt`；探针原始输出见同文件「原始探针输出」节）

| idle（重复） | — | 0.395868 | 1.0% | — |

离散度（同参数重复两遍，同窗口 W2=40s）：

* idle：`0.358832` vs `0.395868` → 差 0.037s（**噪声 ~0.04s CPU / 40s ≈ 0.1%**）
* hover 300：`38.627473` vs `35.455436` → 差 3.17s（约 8%，两个都接近满核）

### 3.2 触发形状确实到位（不是「测了个寂寞」）

| 场景 | socks_up | held（客户端自报） | socks_ok（=REALITY 握手成功） | lsof_estab（本机到 :8543 的 ESTABLISHED 行数） | hover 期间 curl |
|---|---|---|---|---|---|
| idle-40 | 1 | — | — | 0 | **200** |
| hoverA-40 (300) | 1 | **300** | **300** | **557** | **000** |
| hoverB-40 (60) | 1 | 60 | 60 | 120 | 200 |
| hoverR-55 (300→关) | 1 | 300 | 300 | 557 | 200（已回落） |

* `held=300 / socks_ok=300`：300 条 CONNECT 全部完成了 SOCKS 应答 ⇒ REALITY 握手全部成功，
  悬停形状是真的，不是「客户端压根没连上」。
* `lsof_estab=557`：宿主上到 8543 的 ESTABLISHED 套接字（含两端），数量与 300 条悬停相符。
* `hover 期间 curl=000`：**自旋时实例确实已经不能转发**（与线上「TCP 能连、无任何响应」同形）；
  同一实例 idle 时 curl=200 ⇒ 这不是「实例本来就坏」。
* 服务端日志 Forwarded 行数：idle=1，hoverA=**0**（自旋期间日志冻住，与 V24 生产现象一致）。

### 3.3 连接数扫描（单窗口，`cpu% = cpu/窗口`，≥50% 记自旋）

| N | 窗口 | cpu | cpu% | 自旋 |
|---|---|---|---|---|
| 100 | 40s | 0.546413 | 1.4% | 否 |
| 150 | 40s | 0.499665 | 1.2% | 否 |
| 200 | 40s | 0.557164 | 1.4% | 否 |
| 250 | 40s | 0.594127 | 1.5% | 否 |

必须让服务端的在途连接数真的顶到上限。

## 4. 最小触发条件

1. **必须是真实现场**：wasm 服务端（`wasi.rs` 平台层）+ 真 REALITY 握手（有真实的读写流量）。
   * 宿主二进制最小探针（`host.rs`，1ms 轮询）**永远测不出来**。
   * wasm 最小探针（socket 层，无协议）在本机**不可靠**：见 §5。
2. **连接数要顶到并发上限**：`MAX_CONCURRENT_CONNS = 256`
   （`crates/xt-wasm-cli/src/server.rs:60`）。实测 100/150/200/250/270 不触发，
   **256 与 300 触发** —— 且非单调，说明取决于「在途数是否真的撞到 256」这个竞态。
3. **目标不可达（`10.255.255.1:5226`）不是必须的**（未逐项验证）；但它能让连接在服务端**停住**，
   从而把在途数顶到上限。250 条那组日志显示服务端 `connect()` 约 3.5s 后 `ConnectFailed`
   ——所以「悬停」其实是「连接不断进来 + 每条停 ~3.5s」的稳态。
4. **必须有一批连接在「握手已完成之后」仍被服务端持有**（V24 九续的结论在本机同样成立）。

## 5. 最小 wasm 探针矩阵（静默 vs 发字节）——**inconclusive，但抓到一个平台差异**

`scripts/v24-cpu-probe.py` 新增 `--hover-quiet`（连接后**一个字节都不发**；默认发 3 轮 15 字节）。
4 个 wasm 探针 × {idle, 静默 8/32/128, 发字节 8/32/128}，窗口 6s，`cpu` 秒：

| probe | idle | 静默8 | 静默32 | 静默128 | 字节8 | 字节32 | 字节128 |
|---|---|---|---|---|---|---|---|
| `stream_spin_probe`（只读） | 0.115 | 0.116 | 0.116 | 0.129 | 0.114 | 0.121 | 0.270 |
| `stream_spin_probe_w`（只写） | 0.121 | 0.111 | 0.117 | 0.123 | 0.105 | 0.120 | 0.127 |
| `stream_spin_probe_rw`（读写交替） | 0.109 | 0.114 | 0.127 | 0.123 | 0.110 | 0.126 | 0.420 |
| `stream_spin_probe_timeout`（读+timeout） | 0.106 | 0.117 | 0.114 | 0.126 | 0.112 | 0.111 | **6.223**（一次） |

**判 `inconclusive`**：干净地基线是「静默悬停」（全部 ≈ idle），而在它上面：
`stream_spin_probe_timeout × 发字节 × 128` 出现过一次 6.22s/6s（≈103%），但**重复两次只有
0.251s / 0.259s** ⇒ 那是一次不可重复的离群值，不能当结论（这与 lead 自己的矩阵判
inconclusive 一致，理由也一致：默认 hover 会发字节，差值里混着「流量本身的工作量」）。

**顺带一个反直觉的平台差异（待证，不作结论）**：Linux 上自旋的是「只写」探针
（V24 十一/十二续，501 ticks），本机「只写」始终 ~0.12s/6s，而「只读 + 有数据到达」在 128 条时
升到 0.27–0.42s。**同一判据下两台机器的热路径不同**，这条值得单独追。

## 6. 根因候选 + 下一步（**给公告板待修队列的建议**）

### 6.1 建议先修/先验的假设：accept 循环的「满员等待」

`crates/xt-wasm-cli/src/server.rs:517-524`（读代码，未改）：

```rust
loop {
    let stream = listener.accept().await?;
    let peer = stream.peer_addr()...;

    while live.get() >= MAX_CONCURRENT_CONNS {   // 256
        sleep(Duration::from_millis(5)).await;   // ← 在 accept 与 spawn_task 之间空转等待
    }
    live.set(live.get() + 1);
    spawn_task(async move { ...; live_task.set(live - 1); });
}
```

它同时满足本次实测的**全部**特征，而且**只有它满足**：

| 观察 | 该候选给出的解释 |
|---|---|
| 触发门槛正好在 256 附近（256 触发、250 不触发） | 只有 `live >= 256` 才会进这段等待 |
| 非单调（270 不触发） | 是否真的撞到 256 取决于连接到达速率 vs 每条 ~3.5s 的生命周期（竞态） |
| 一旦开始就**永不恢复**、日志冻住 | 单线程协作式运行时里这段忙等把已 spawn 的任务也饿死 ⇒ `live` 永不回落 ⇒ 循环永不退出 |
| timer 类超时全部失效（V24 二十一续） | 自旋本身就发生在一个 **timer sleep** 上；定时器被自己的忙等饿死 |
| 只读/只写的 socket 层探针都不复现 | 它们没有 256 的上限，永远不会进这段等待 |

### 6.2 判据（修完必须过的三条，全部已在 `scripts/v24-field-test.sh` 里做成一键）

1. `hover 300 条` 的 `marginal < 0.15`（当前 1.0862）；
2. 悬停期间 `curl = 200`（当前 000）——**CPU 低不算数，功能必须同时在**；
3. 回落实验 `marginal < 0.15`（当前 -0.9886，已过；防「用阻塞换忙等」）。

### 6.3 最小、最直接的验证实验（建议由 lead 指派给能动 `crates/**` 的人）

**不改机制、只改这一段的形状做对照**（一次只改一处，V24 的纪律）：

* 变体 A：把 `while live >= 256 { sleep(5ms) }` 移进 `spawn_task` 里（accept 永不停）——
  若 300 条不再自旋且 curl=200，则机制坐实；
* 变体 B：满员时直接 `drop(stream)`（接受后立刻关闭）——用来区分「等待逻辑」与「未消费的已接受流」。

两个变体都只需跑 `scripts/v24-field-test.sh`（缓存已存，核心场景几秒出结果）。

### 6.4 与 V27 的关系（lead 的跨线假设，本次未测）

lead 怀疑 V24/V27 同根（客户端侧也在忙等）。**本次没有测客户端侧 CPU**（第二优先级，
时间用在了把服务端判据做实 + 连接数扫描上）。已排除的只有：服务端这侧的自旋**不是**
wstd/wasmtime 单独的问题（纯 wstd 只读/只连/只写在本机都不自旋），而是**我们的代码**
（accept 上限等待 / 协议层用法）。客户端侧要按 lead 给的命令单独测，**未验证**。

## 7. 未验证 / 边界（不许当成结论）

* **生产是 Linux**。本结论是 macOS 本机（wasmtime 48.0.2 aarch64-macos）的实测；
  Linux 上仍以 `scripts/e2e-spin-test.sh` 为准。本机复现**支持**（不证明）「V24 与平台无关」。
* **256 门槛是竞态不是阈值**：256 触发、270 不触发，说明还需要更细的时序刻画（未做）。
* **6.1 是根因候选，不是结论**：我没有改 `crates/**`（写入范围限制），所以没有做变体 A/B 的对照。
* **最小探针矩阵判 inconclusive**：那个 6.22s 的离群值未解释。
* **回落实验**只证明「关掉连接后 CPU 回落」，不证明「修好了」。
* 本次现场用的是**干净 HEAD 构建**（sha256 `99efd472…`），因为共享工作区里有队友未提交的
  `crates/xt-wasm-runtime/src/wasi.rs`（186 行改动）把仓库里的 wasm 产物换过字节；
  这保证了「测的是 v0.7.0」，但也意味着**没有**覆盖队友的在途改动。
