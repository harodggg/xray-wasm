## 1. 服务端冷/热：没有惩罚

### 1.1 真 REALITY 认证裸探针

`./scripts/v27-cold-warm.sh latency`（`XW_V27B_RUNS=2`，2026-09-20 17:5x，端口 8643）：
用 server.json 的 privateKey 现算公钥、按 REALITY 客户端语义封装 session_id
（X25519 + HKDF-SHA256(salt=random[0:20], info=b"REALITY") + AES-256-GCM(AAD=整条 ClientHello)），
**走认证路径**（会连 dest 取证书），只读到 ServerHello 为止。

```
  对照：直连 dest (www.cloudflare.com:443)
direct 221.3 221.3 ServerHello len=122
  冷/热：每轮重启服务端（真冷启动），连测 3 条
  轮 1 冷: c1 414.7 414.8 ServerHello len=122
  轮 1 热: c2 456.2 456.3 ServerHello len=122
  轮 1 热: c3 422.9 422.9 ServerHello len=122
        服务端日志: 3 条 Server Hello, 0 条认证失败
  轮 2 冷: c1 460.1 460.2 ServerHello len=122
  轮 2 热: c2 406.5 406.5 ServerHello len=122
  轮 2 热: c3 459.0 459.0 ServerHello len=122
        服务端日志: 3 条 Server Hello, 0 条认证失败
```

同一天更早（17:36，机器较空闲）的一次同样结构：直连 231.1/235.3ms；冷启动 xray 第一连
215.9ms，第 2/3 连 225.9/236.7ms。**两份都显示「冷 ≈ 热 ≈ 直连 dest 的 RTT」**，
服务端日志同时给出 `Server Hello: 127` 与 `hs.handshake() err: <nil>`，证明走的是认证路径而不是
「认证失败回退成中继」那条路。

### 1.2 `--self-test`（只做 REALITY 握手，每样本新进程）

对**每次新启的冷启动服务端**（17:38，v0.7.0 发布产物 475071 字节）：

```
  self-test#1: ✓ REALITY 握手完成，用时 245.526166ms    self-test#1: 215.766208ms    self-test#1: 657.316792ms
  self-test#2: ✓ 250.368042ms                            self-test#2: 253.17725ms     self-test#2: 244.600333ms
  self-test#3: ✓ 217.200458ms                            self-test#3: 308.702542ms    self-test#3: 235.5895ms
```

⇒ **「官方服务端冷启动」不是 V27 的根因**。本仓库文档 §2 里那条「首连要连 dest 取证书、飞行包
晚 ~1.5s」的假设，在本机今天的两次独立测量里都**不成立**。这条是 B1/B2 的全部意义所在：
把 V27 与「冷启动」解耦。

## 2. 首连时间分解（10 次）

`./scripts/v27-cold-warm.sh table`（`XW_V27B_SAMPLES=5`，17:52–17:55，冷启动服务端 8643 + wasm 客户端 1091；
被测 wasm sha256 `74ffa736…`）。服务端与客户端日志都用同一绝对时钟打点。

场景 (a) 干净首连；(b) 先做 e2e-test.sh 第 3/4 步那种「认证被拒的 SOCKS 连接」再首连。

| a1 | 200 | +0.022 | +1.391 | +6.393 | +7.141 |
| a2 | 200 | +0.019 | +0.456 | +10.458 | +11.400 |
| a3 | 200 | +0.018 | +0.432 | +5.433 | +6.359 |
| a4 | 200 | +0.020 | +1.465 | +6.468 | +7.151 |
| a5 | 200 | +0.021 | +0.453 | +5.455 | +7.035 |
| b1 | 200 | +0.022 | +0.456 | +5.458 | +7.697 |
| b2 | 200 | +0.017 | +0.451 | +5.453 | +6.531 |
| b3 | 200 | +0.017 | +0.443 | +5.444 | +6.385 |
| b4 | 200 | +0.016 | +0.508 | +5.510 | +7.384 |
| b5 | 200 | +0.015 | +0.452 | +5.453 | +6.106 |

**关键观察**：`ServerHello → 服务端收到 VLESS 头` 的差值 = **5.002 / 10.002 / 5.001 / 5.003 / 5.002 /
5.002 / 5.002 / 5.001 / 5.002 / 5.001**。精确到毫秒的量化，不是网络抖动：

* 它解释了 flaky：1 个节拍 ≈ 5.5s（稳过）；2 个节拍 ≈ 10.5s，而 REALITY 死线是 10s →
  有时擦线成功（a2 的 11.4s 仍 200），有时失败（§5 的 e2e #7）。
* 它**不是** REALITY 握手：服务端在 ServerHello 同一毫秒就读到了客户端 Finished（见
  `v27-five-second.md`）。所以「10s 死线」与「5s 节拍」是两条不同的路径。

### 2.1 只有「进程的第一条隧道」慢（6 次序列请求）

同一客户端进程、同一冷启动服务端，连续 4 条请求（17:37–17:39，v0.7.0 发布产物；`nc -z` 探活算一条
SOCKS 连接）：

```
  轮 1: req#1 -> 200 5.674377 | req#2 -> 200 0.536288 | req#3 -> 200 0.604728
  轮 2: req#1 -> 200 5.534606 | req#2 -> 200 0.645973 | req#3 -> 200 0.533361
  轮 3: req#1 -> 200 5.564140 | req#2 -> 200 0.530169 | req#3 -> 200 0.541388
  轮 4: req#1 -> 200 5.559665 | req#2 -> 200 0.580674 | req#3 -> 200 0.806384
  轮 5: req#1 -> 200 5.559561 | req#2 -> 200 0.557602 | req#3 -> 200 0.555229
  轮 6: req#1 -> 200 5.593484 | req#2 -> 200 0.560491 | req#3 -> 200 0.558212
```

⇒ **首连 ~5.5s、其后 ~0.55s**，且与「服务端冷/热」「有没有前置被拒连接」都无关。
这是 §6 兜底推算的依据：**重试用的新连接是快的那一类**（但它是不是「第一条」取决于实现——
若重试发生在同一进程内、首连已占用掉那个一次性状态，则重试快）。

## 5. 真 e2e-test.sh：冷启动服务端上 N=10 → 8 PASS / 2 FAIL

`./scripts/v27-cold-warm.sh e2e`（`XW_V27B_E2E_N=10`；自建一次性配置 8643，SOCKS 1091；

  #2 PASS  16.3s  wasm-sha8=38835baa
  #3 PASS  16.3s  wasm-sha8=38835baa
  #4 PASS  16.0s  wasm-sha8=22b13bd2
  #5 PASS  16.3s  wasm-sha8=22b13bd2
  #6 FAIL   5.6s  wasm-sha8=22b13bd2  ✗ curl 失败
  #7 FAIL  13.6s  wasm-sha8=22b13bd2  ✗ curl 失败

**判据结论**：`task-8` 要求的「兜底能否让 e2e-test.sh 稳定 8/8」——**当前 8/10 不稳**。
而且这次 8/10 还是在没有专门加负载的情况下测到的；§2 的 2 节拍命中就会翻红。

## 6. 兜底：失败后**重试一次新连接**

### 6.1 脚本级等价验证（`mode_retry`）

每次重试都是**全新的 SOCKS 连接 → 全新 TCP + 全新 ClientHello**，与「在客户端内部重试」的代价同构；
脚本会复刻 e2e 第 3/4 步，再发首个隧道请求；首连失败才发第二次。

```
不加载（SAMPLES=10）：首连成功 10/10，用时 5.49/5.70/5.90/5.64/5.57/5.53/5.71/5.51/5.53/5.48s
自加 12 个 CPU 忙循环（SAMPLES=6）：首连成功 6/6，5.61/5.61/10.58/5.73/5.61/5.56s
```

* **失败样本没被触发**（0/16），所以「失败→重试→成功」这条链**没有得到直接实测证据**。
* 但间接推算成立：e2e #7 的失败在 ~10s 被检测到，而同一客户端进程里**第 2/3 条隧道稳定 ~0.55s**
  （§2.1）⇒ 重试一次 ≈ 10s + 0.6s ≈ **10.6s**，落在 e2e 第 5 步 `curl -m 30` 之内。
* **反例风险（真实存在）**：17:42 那次我曾观测到失败是在 **curl -m 30 超时之后（~36.3s）**
  才被日志记录 —— 因为死线的 wall-clock 检查只在任务被重新 poll 时才执行。若失败总是在此时
  才浮出，重试就会晚于 curl 的 30s 预算，**兜底失效**。所以：**重试是兜底，不是修复；它的
  有效性取决于失败被检测到的时刻，本机两种情况都出现过（未验证其分布）。**

### 6.2 代价（写清楚）

* 每次兜底重试多 **1 条 TCP 连接 + 1 次完整 REALITY ClientHello**（chrome profile，~1.8KB，
  扩展顺序/GREASE 本来就每连接随机，不会让跨连接指纹变一致）。
* 服务端侧多一次「连 dest 取证书 + 伪造证书飞行包」的完整工作（~2.7KB 飞行包）。
* 失败请求的延迟从 ~10s 变成 ~10.6s（乐观）到 ~40s（悲观）；不失败时零代价。
* 若改成「并发对冲」（2s 后起第二条连接，取先到者），代价是正常路径也可能多一条连接，
  但能绕开「失败检测晚」这个致命点。**未实测。**

### 6.3 lead 的裁定

lead 已明确：**不给 `main.rs` 写入范围**（理由正是「失败可能在 curl 超时之后才被检测到」），
本任务只做脚本级等价验证。故生产代码一行未改。

## 8. 给下游的三条建议

1. **公告板 §2 的冷启动归因可以撤掉**：本机两次独立测量都显示冷启动服务端 ≤0.46s 发 ServerHello，
   且握手只要 ~0.25s（另有 `--self-test` 样本）。V27 不是冷启动属性。
2. **把 V27 拆成两条线**：(i) 客户端「首个应用写」的 5s/10s 节拍（task-21 已定位到客户端侧）；
   (ii) 服务端/链路首个飞行包晚于死线（v27-wake 在其窗口测到 17.1–19.3s）。两者都能让 e2e 红。
3. **`e2e-test.sh` 目前不稳定（8/10），不能作为「修好了」的终判**；建议回归判据用
   `scripts/v27-regress.sh` 那种不依赖官方二进制、可数 tick 的判据，并把「首连耗时分布」纳入判据。
