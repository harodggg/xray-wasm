# V27 终局：官方 Xray 服务端的**一次性初始化 5s**，客户端消不掉（含三轮实验原始数据）

作者：lead · 2026-09-21 · 对象：`docs/issue-board.md` §2（V27）

## 结论（先给结论）

那 5s 是**官方 Xray 服务端进程启动后第一次建隧道连接时的一次性初始化**。客户端能做的只有两件事：

1. **握手超时重试**（已发布，v0.7.1）：首连超时时换新连接重试一次；
2. **启动时预热**：让「初始化窗口」提前发生。

但**预热并不能让「客户端启动后马上到达的第一条请求」变快** —— 实验数据（下方 §3）显示：
初始化进行中到达的连接同样要等到初始化结束。只有**初始化完成之后**发出的连接才是 ~0.2–0.3s。

⇒ 彻底的修法是**部署侧的就绪门**（客户端在预热完成前不报告「可用」）。这改变启动契约，
因此不作为代码默认行为提交，留给部署方决定。

## 1. 被证伪的假设：「Finished 与首条应用记录同突发 ⇒ 服务端只对新到达字节收通知」

做法：给客户端加研究开关 `XT_FIRST_RECORD_DELAY_MS`（握手完成后、写首条应用记录之前插入延迟），
用 `scripts/v27-cold-warm.sh table`（真官方服务端 + 真 curl，冷启动每次）测同一个量
`+VLESS-at-server`（服务端日志里首条应用记录**被处理**的时刻，相对 curl 起点的绝对秒数）。

| 客户端错开 | 样本 | ClientHello | ServerHello | **VLESS-at-server** | curl TTFB |
|---|---|---|---|---|---|
| 0ms（基线） | 5 | +0.02…0.03 | +0.40…0.46 | **+5.40…+5.46** | 5.76–6.09s |
| **30ms** | 3 | +0.03…0.04 | +0.25…1.19 | **+5.25…+5.27**（第 3 例 +6.20 随 ServerHello 漂移） | 5.56–6.48s |
| **1000ms** | 3 | +0.02…0.03 | +0.25…0.25 | **+5.25…+5.25** | 5.55–5.63s |

**读法**：`+VLESS-at-server − +ServerHello ≈ 5.00s`，**与客户端什么时候发首条应用记录无关**
（错开 30ms、1000ms 都一样）。若真是「同突发导致丢通知」，1s 的错开必然让服务端提前处理。
⇒ **假设证伪**；形状是服务端侧的**固定计时器**。

顺带得到一条次要结论：`table` 的 (b) 组（先做两次「认证被拒的 SOCKS 连接」）
**并不构成预热** —— 那两次在 SOCKS5 认证阶段就被本地拒了，根本没建隧道，所以两组数字无差别。

## 2. 预热实现与它的真实效果

实现（研究代码，未提交）：客户端启动时在 bind 之前 `spawn_task` 起一条一次性隧道
（`open_tunnel` → 写一条 `GET / HTTP/1.0` → **等第一个响应字节**再丢弃），
`XT_NO_WARMUP=1` 关闭。要点：

* 只握手不算预热：实测「握手完成」0.25s 就返回，什么都没吸收；必须等到第一个响应字节。
* 必须**不阻塞**：若在 bind 之前 `await` 预热，客户端会 5s 不监听 ——
  `scripts/v27-cold-warm.sh e2e` 直接报 **0/3**「wasm 客户端没有监听 127.0.0.1:1091」。

异步化之后的验证：

| 实验 | 结果 |
|---|---|
| `v27-cold-warm.sh e2e`（真 e2e-test.sh ×3，冷启动官方服务端） | **3/3 PASS**（17.8s / 32.5s / 26.7s） |
| `v27-cold-warm.sh table`（有预热时测用户首条请求） | 预热日志 `预热完成：5.50s` ✓，**但 curl TTFB 仍 5.54–5.59s**，`+VLESS-at-server=+5.26` |

最后一行是关键：**预热吸收了初始化，可它没让首条用户请求变快** ——
因为那条请求在初始化窗口内到达（`+ClientHello=-0.07`，即在 curl 起点之前 70ms，
那是预热自己的连接）。这与 §2 板子上 req2/req3 很快并不矛盾：那两条是在 req1 **完成之后**才发的。

## 3. 为什么不作为默认行为提交

* 预热对「启动后就立刻发请求」的调用方（e2e、探针、急用户）**没有收益**；
* 它换来一次额外连接与一个额外的日志行，却可能被读成「V27 已修」——**这是最坏的后果**；
* 真正有效的修法是**就绪门**（预热完成前不报告可用），那要改启动契约，
  且会让现有「端口一开就 curl」的工具链超时（实测 v27 脚本 3.6s 就判定失败）。

## 4. 留给下游/上游的处置建议

1. **部署侧**（推荐）：readinessProbe 在预热完成前不通过（例如客户端加 `XT_READY_FILE` 或
   新增 `--warmup-gate`）；这样「首条用户请求」永远落在初始化之后，实测 ~0.2–0.3s。
2. **上游**：这是官方 Xray 服务端的行为（首连恒定 +5.00s），值得作为 issue 反馈；
   我们这边已有可复现的最小证据链（`scripts/v27-cold-warm.sh table`）。
3. **现状**：v0.7.1 里的握手重试已经覆盖「首连超时导致失败」这一类；首连**延迟**仍在。
